\section*{Abstract}
\addcontentsline{toc}{section}{Abstract}

The present research project exposes the development of an Inventory Management System
for a retail toy store, designed under the Object-Oriented Programming (OOP) paradigm
using the PHP language through the \emph{Laravel} framework. The proposal arises given
the deficiencies identified in manual stock control and the lack of real-time
synchronization, which negatively impacts business profitability. Through a
\emph{Model-View-Controller} (MVC) architecture that implements the \emph{Eloquent ORM}
object-relational mapping and \emph{Blade} view templates, a modular, scalable, and highly
portable web application is offered. Structured persistence and hierarchical control by
categories and brands ensure data integrity, optimizing audits and allowing informed
decision-making based on automated reports.

\emph{Keywords:} inventory, Object-Oriented Programming, PHP, Laravel, Eloquent, toy store.

\section*{Resumen}
\addcontentsline{toc}{section}{Resumen}

El presente proyecto de investigación expone el desarrollo de un Sistema de
Gestión de Inventario para una juguetería minorista, diseñado bajo el
paradigma de la Programación Orientada a Objetos (POO) empleando el lenguaje
PHP a través del framework \emph{Laravel}. La propuesta surge ante las
deficiencias identificadas en el control manual de existencias y la falta de
sincronización en tiempo real, lo cual impacta negativamente la rentabilidad
empresarial. A través de una arquitectura \emph{Modelo-Vista-Controlador}
(MVC) que implementa el mapeo objeto-relacional \emph{Eloquent ORM} y las
plantillas de vista \emph{Blade}, se ofrece una aplicación web modular,
escalable y altamente portable. La persistencia estructurada y el control
jerárquico por categorías y marcas aseguran la integridad de los datos,
optimizando las auditorías y permitiendo una toma de decisiones informada
basada en reportes automatizados.

\emph{Palabras clave:} inventario, Programación Orientada a Objetos, PHP,
Laravel, Eloquent, juguetería.

\section{CAP\'ITULO 1: JUSTIFICACI\'ON DEL PROYECTO}

\subsection{1.1 Planteamiento del problema general y justificaci\'on del proyecto}

La gesti\'on de inventarios en una jugueter\'ia minorista enfrenta desaf\'ios
cr\'iticos debido a la alta rotaci\'on de productos y la diversidad de categor\'ias
que deben administrarse. Actualmente, el uso de m\'etodos manuales o registros en
hojas de c\'alculo aisladas ha evidenciado limitaciones estructurales en el
modelo operativo (Welling y Thompson, 2017). Esta pr\'actica convencional genera
tres problemas operativos fundamentales que afectan la rentabilidad y la
eficiencia del negocio:

\begin{itemize}
  \item \textbf{Deficiencia en el control de stock por categor\'ias y marcas:}
        la ausencia de una clasificaci\'on sistematizada impide una organizaci\'on
        jer\'arquica eficiente, dificultando la localizaci\'on y el seguimiento de
        juguetes seg\'un su fabricante o grupo de edad.
  \item \textbf{Invisibilidad de existencias en tiempo real:} la falta de
        sincronizaci\'on entre las ventas realizadas y el registro de almac\'en
        imposibilita conocer la disponibilidad inmediata de los productos.
  \item \textbf{Ineficiencia en procesos manuales e inventarios f\'isicos:}
        el procesamiento manual de ventas y la ejecuci\'on de auditor\'ias f\'isicas
        peri\'odicas consumen recursos humanos de forma excesiva.
\end{itemize}

El Sistema de Gesti\'on de Inventario para la jugueter\'ia ``Mundo del Juguete'' resolver\'a la fragmentaci\'on
de datos mediante la centralizaci\'on de operaciones en una aplicaci\'on web
nativa e independiente basada en el paradigma de la Programaci\'on Orientada a
Objetos (POO) mediante el framework Laravel (Stauffer, 2019). Al prescindir de
dependencias de escritorio pesadas, la soluci\'on garantiza agilidad, control
preciso de existencias y portabilidad, requiriendo \'unicamente un servidor web
con PHP y un gestor de base de datos relacional MySQL.

\subsection{1.2 Objetivo general}

Desarrollar una aplicaci\'on web utilizando PHP y Laravel que automatice la
gesti\'on de inventario y punto de venta de una jugueter\'ia, optimizando el control de productos,
stock, compras y categor\'ias mediante una arquitectura modular orientada a objetos que
garantice la integridad y persistencia de la informaci\'on.

\subsection{1.3 Objetivos espec\'ificos}

\begin{itemize}
  \item \textbf{OE1:} Automatizar el control de existencias, compras y reposici\'on mediante alertas tempranas de stock m\'inimo y registro estructurado de recepciones f\'isicas.
  \item \textbf{OE2:} Implementar un m\'odulo de punto de venta (POS) y facturaci\'on que valide la disponibilidad en tiempo real y emita comprobantes legales (boleta/factura).
  \item \textbf{OE3:} Proveer trazabilidad integral y auditor\'ia f\'isica mediante kardex sistematizado y matriz de trazabilidad entre requerimientos y componentes del software.
  \item \textbf{OE4:} Dise\~nar una arquitectura en tres capas (Presentaci\'on, L\'ogica de Negocio y Dominio) bajo el patr\'on Modelo-Vista-Controlador (MVC) en Laravel y persistencia relacional con Eloquent ORM.
\end{itemize}

\section{CAP\'ITULO 2: MARCO TE\'ORICO REFERENCIAL O DISE\~NO METODOL\'OGICO}

\subsection{2.1 Marco Te\'orico y Tecnol\'ogico}

Para fundamentar la construcci\'on del software bajo est\'andares t\'ecnicos de la
industria, se describen las tecnolog\'ias y conceptos asociados a PHP y Laravel
que constituir\'an la estructura del sistema (PHP Documentation Group, 2024):

\begin{description}
  \item[PHP:] lenguaje de scripting del lado del servidor que provee un motor
        de ejecuci\'on s\'incrono, gesti\'on de memoria y APIs est\'andares
        de control de datos sin requerir componentes externos.
  \item[Laravel:] framework MVC para PHP que facilita el desarrollo de
        aplicaciones web mediante rutas, controladores y migraciones de base de datos (Stauffer, 2019).
  \item[Herencia y Polimorfismo:] mecanismos de POO que se emplean para
        definir clases base y especializar comportamientos en el dominio (Welling y Thompson, 2017).
  \item[Eloquent ORM:] mapeo objeto-relacional de Laravel que act\'ua como
        puente de comunicaci\'on directo con el motor de base de datos relacional MySQL.
  \item[Blade \& CSS:] motor de plantillas de Laravel para la maquetaci\'on din\'amica y responsiva de la interfaz web.
\end{description}

\subsection{2.2 Metodolog\'ia de Desarrollo: Enfoque Cascada (Waterfall)}

El proyecto adopta formalmente el modelo de ciclo de vida tradicional en Cascada (\emph{Waterfall}) (Pressman y Maxim, 2021; Sommerville, 2011), caracterizado por una ejecuci\'on secuencial y rigurosa estructurada en fases consecutivas:

\begin{enumerate}
    \item \textbf{Fase de Ingenier\'ia de Requerimientos:} Levantamiento exhaustivo de las necesidades del negocio de jugueter\'ia, especificaci\'on de Casos de Uso del Negocio (CUN), delimitaci\'on de Requerimientos Funcionales (RF) y No Funcionales (RNF), y validaci\'on de reglas de negocio.
    \item \textbf{Fase de An\'alisis y Dise\~no del Sistema:} Modelado estructural y din\'amico mediante UML (Casos de Uso del Sistema CUS, prototipos UI/UX, diagramas de secuencia BCE, diagramas de estados y diagrama de paquetes en tres capas).
    \item \textbf{Fase de Implementaci\'on y Codificaci\'on:} Desarrollo modular de los modelos Eloquent, migraciones de base de datos MySQL, controladores transaccionales y vistas Blade en PHP 8.2+.
    \item \textbf{Fase de Verificaci\'on y Pruebas (QA):} Ejecuci\'on de casos de prueba unitarios y de integraci\'on con PHPUnit para garantizar la integridad referencial y la ausencia de defectos antes de la puesta en producci\'on.
    \item \textbf{Fase de Despliegue y Mantenimiento:} Entrega operativa de la soluci\'on y planificaci\'on de mantenimientos preventivos y evolutivos.
\end{enumerate}

La elecci\'on del enfoque Cascada responde a la necesidad acad\'emica y t\'ecnica de asegurar que los artefactos de requerimientos y dise\~no est\'en 100\% validados antes de iniciar la programaci\'on, minimizando retrabajos y garantizando una trazabilidad total entre la l\'ogica del negocio y el c\'odigo fuente.

\section{CAP\'ITULO 3: DESARROLLO DE LA SOLUCI\'ON}

En este ac\'apite se anexa y organiza el desarrollo completo del contenido del proyecto, estructurado de acuerdo con el calendario de avances y entregables por fases requeridos a lo largo del ciclo acad\'emico:

\subsection{3.1 Primer grupo de entregables - Semana 5}

\subsubsection{3.1.1 Descripci\'on de la organizaci\'on objetivo y el negocio}

La empresa objetivo es la jugueter\'ia minorista ``Mundo del Juguete'', dedicada a la comercializaci\'on de juguetes educativos, figuras de acci\'on, juegos de mesa y art\'iculos recreativos infantiles. La organizaci\'on busca transformar su operaci\'on tradicional basada en registros en papel y hojas de c\'alculo hacia una plataforma web centralizada que garantice consistencia de inventario en tiempo real, agilidad en el punto de venta y planificaci\'on oportuna de compras a proveedores.

\subsubsection{3.1.2 Especificaci\'on de los actores, trabajadores, casos de uso y entidades del negocio}

A continuaci\'on se definen los participantes y elementos que componen el modelo del negocio:
\begin{itemize}
  \item \textbf{Actores del Negocio:} Cliente (persona natural o jur\'idica que adquiere art\'iculos en tienda) y Proveedor (empresa distribuidora o f\'abrica que suministra lotes de juguetes).
  \item \textbf{Trabajadores del Negocio:} Administrador (gestor de compras y auditor\'ias), Vendedor (encargado del punto de venta), Cajero (responsable de cobros y facturaci\'on) y Encargado de Almac\'en (responsable de la recepci\'on y estiba de mercanc\'ia).
  \item \textbf{Casos de Uso del Negocio (CUN):} CUN-01 (Gestionar Ventas), CUN-02 (Gestionar Abastecimiento), CUN-03 (Controlar Inventario), CUN-04 (Gestionar Devoluciones y Cambios), CUN-05 (Flujo Interno de Venta y Reposici\'on) y CUN-06 (Flujo Externo con Proveedores).
  \item \textbf{Entidades del Negocio:} Usuario, Cliente, Proveedor, Producto, Categor\'ia, Venta, DetalleVenta, OrdenCompra, DetalleCompra y Comprobante.
\end{itemize}

\subsubsection{3.2.2 Descripci\'on actualizada de Requerimientos Funcionales / No Funcionales}

Los requerimientos del sistema formalizan las necesidades operativas de la juguetería minorista, categorizados en Requerimientos Funcionales (RF-01 a RF-31) y Requerimientos No Funcionales (RNF-01 a RNF-06), vinculados de manera biunívoca a los procesos de negocio.

\paragraph{Requerimientos Funcionales (RF):}

\begin{itemize}
  \item \textbf{RF-01 (Inicio de Sesión):} El sistema debe permitir el acceso exclusivo a los usuarios autorizados (vendedor, cajero, administrador, almacenero) mediante credenciales cifradas antes de permitir cualquier operación comercial o administrativa.
  \item \textbf{RF-02 (Selección de Productos):} El sistema debe permitir buscar y seleccionar juguetes por código SKU, código de barras, nombre comercial, categoría o marca.
  \item \textbf{RF-03 (Validación de Stock en Tiempo Real):} El sistema debe verificar la disponibilidad de existencias antes de autorizar el registro o la reserva de los productos solicitados.
  \item \textbf{RF-04 (Procesamiento de Venta y Comprobante):} El sistema debe registrar la transacción vinculando al cliente, ítems, precios, impuestos y emitir boleta o factura con serie legal correlativa.
  \item \textbf{RF-05 (Actualización Automática de Inventario):} El sistema debe descontar inmediatamente las unidades vendidas del stock disponible tras confirmarse el pago.
  \item \textbf{RF-06 (Control de Excepciones de Stock):} El sistema debe alertar y bloquear transacciones comerciales si la cantidad solicitada excede el saldo en almacén.
  \item \textbf{RF-07 (Detección de Stock Crítico):} El sistema debe emitir alertas tempranas automáticas al administrador cuando las existencias alcancen o sean inferiores al stock de seguridad.
  \item \textbf{RF-08 (Cotización a Proveedores):} El sistema debe registrar y gestionar las cotizaciones de compra solicitadas a los proveedores autorizados.
  \item \textbf{RF-09 (Emisión de Órdenes de Compra):} El sistema debe generar y transmitir órdenes de compra formales numeradas hacia los distribuidores externos.
  \item \textbf{RF-10 (Registro de Recepción Física):} El sistema debe registrar la llegada física de la mercancía con verificación de bultos y notas de remisión.
  \item \textbf{RF-11 (Actualización de Stock por Compra):} El sistema debe incrementar automáticamente las existencias disponibles en el kardex tras confirmarse la recepción.
  \item \textbf{RF-12 (Acceso al Control de Inventario):} El sistema debe restringir el módulo de auditorías y ajustes de existencias únicamente al rol Administrador.
  \item \textbf{RF-13 (Registro de Auditorías Físicas):} El sistema debe asentar conteos físicos periódicos y comparar saldos reales frente al saldo del software.
  \item \textbf{RF-14 (Registro de Mermas y Roturas):} El sistema debe documentar bajas de artículos por deterioro, rotura o robo con sustento justificado.
  \item \textbf{RF-15 (Ajuste de Existencias y Niveles Mínimos):} El sistema debe recalibrar el stock disponible y los umbrales mínimos según los resultados de auditoría.
  \item \textbf{RF-16 (Emisión de Reportes de Kardex):} El sistema debe exportar reportes detallados de movimientos valorizados en formato PDF y Excel.
  \item \textbf{RF-17 (Registro de Solicitudes de Devolución):} El sistema debe registrar solicitudes de clientes por fallas de fábrica o cambios de producto.
  \item \textbf{RF-18 (Validación de Comprobante Original):} El sistema debe cotejar el comprobante original de compra para habilitar cualquier trámite de garantía.
  \item \textbf{RF-19 (Control de Plazos y Políticas de Devolución):} El sistema debe verificar que la solicitud no sobrepase los 7 días hábiles desde la fecha de compra.
  \item \textbf{RF-20 (Procesamiento de Cambio o Reembolso):} El sistema debe procesar el cambio por un producto similar o autorizar la devolución de fondos.
  \item \textbf{RF-21 (Generación de Notas de Crédito):} El sistema debe emitir la nota de crédito electrónica asociada y reingresar el producto al stock de revisión o descarte.
  \item \textbf{RF-22 (Venta Integrada con Kardex):} El sistema debe sincronizar el descuento de inventario con la emisión transaccional de caja.
  \item \textbf{RF-23 (Cierre de Caja y Facturación):} El sistema debe totalizar los ingresos por turno distinguiendo efectivo, tarjetas y transferencias digitales.
  \item \textbf{RF-24 (Solicitud Preventiva de Reposición):} El sistema debe permitir al administrador generar borradores de compra basados en la rotación de ventas.
  \item \textbf{RF-25 (Conformidad de Entrega en Bodega):} El sistema debe emitir constancias de ingreso con firma digital del almacenero.
  \item \textbf{RF-26 (Atención Comercial a Clientes):} El sistema debe permitir registrar cotizaciones preliminares para clientes mayoristas o corporativos.
  \item \textbf{RF-27 (Historial de Compras por Cliente):} El sistema debe almacenar el histórico de consumos por DNI o RUC para planes de fidelización.
  \item \textbf{RF-28 (Despacho y Entrega Final):} El sistema debe registrar la entrega física del juguete al cliente en el mostrador de empaque.
  \item \textbf{RF-29 (Evaluación de Desempeño de Proveedores):} El sistema debe clasificar proveedores según tiempos de entrega y cumplimiento de pedidos.
  \item \textbf{RF-30 (Registro de Guías de Remisión):} El sistema debe vincular las órdenes de compra con las guías de remisión física del transportista.
  \item \textbf{RF-31 (Conciliación Definitiva de Existencias):} El sistema debe cerrar los ciclos de recepción conciliando facturas de compra y órdenes emitidas.
\end{itemize}

\paragraph{Requerimientos No Funcionales (RNF):}

\begin{itemize}
  \item \textbf{RNF-01 (Rendimiento):} Las consultas de disponibilidad y el procesamiento de ventas en el POS deben responder en menos de 2.0 segundos bajo carga normal.
  \item \textbf{RNF-02 (Disponibilidad):} La aplicación debe operar con una disponibilidad mínima del 99.5\% durante los horarios de atención comercial de la tienda.
  \item \textbf{RNF-03 (Seguridad):} El control de accesos se gestiona mediante autenticación robusta y control de permisos por roles (RBAC) con contraseñas hasheadas en Bcrypt.
  \item \textbf{RNF-04 (Concurrencia e Integridad):} El motor de base de datos MySQL debe procesar operaciones transaccionales mediante bloqueos optimistas y aislamiento ACID para evitar sobreventa concurrente.
  \item \textbf{RNF-05 (Usabilidad):} La interfaz web debe ser responsiva, intuitiva y accesible, reduciendo la curva de aprendizaje a menos de 2 horas para personal nuevo.
  \item \textbf{RNF-06 (Respaldo y Recuperación):} Se deben ejecutar copias de seguridad automáticas diarias de la base de datos con un RPO menor a 24 horas y RTO menor a 1 hora.
\end{itemize}

\paragraph{Reglas de Negocio Vinculadas:}

De acuerdo con la operativa comercial de la juguetería ``Mundo del Juguete'', se formalizan las siguientes cinco reglas de negocio que restringen y guían las operaciones:

\begin{itemize}
  \item \textbf{Regla de estímulo y respuesta (RN-01):} Si el proveedor mayorista no confirma la orden de abastecimiento en un plazo máximo de 72 horas, el sistema genera automáticamente una alerta de retraso de pedido y notifica al panel del Administrador para que aplique compras de contingencia.
  \item \textbf{Regla de operación (RN-02):} Para concretar y registrar una venta en el sistema, el Vendedor o Cajero debe encontrarse autenticado con sesión activa, y el producto seleccionado debe contar con un nivel de stock disponible mayor a cero en el almacén.
  \item \textbf{Regla de estructura (RN-03):} Por cada transacción de venta completada, el sistema genera de forma obligatoria un comprobante electrónico con serie y correlativo único (B001 para boletas, F001 para facturas). Un comprobante puede contener múltiples ítems sin límite, siempre que la cantidad no exceda las existencias.
  \item \textbf{Regla de inferencia (RN-04):} Un juguete o producto cuyo inventario físico no presente ningún movimiento de salida (cero ventas) durante un periodo continuo de 6 meses, es catalogado y etiquetado automáticamente por el software como «Producto de baja rotación» para posteriores promociones o liquidaciones.
  \item \textbf{Regla de cálculo (RN-05):} El cálculo del monto total de una venta se obtiene sumando los subtotales de cada ítem en el detalle de la venta. El subtotal de cada ítem se define mediante la fórmula: $\text{Subtotal} = \text{Precio Unitario} \times \text{Cantidad}$. El Impuesto General a las Ventas (IGV del 18\%) se encuentra incluido en el Precio Unitario final del catálogo.
\end{itemize}

\paragraph{Concepto del Diagrama de Clases de Negocio:}
En el marco del modelado de procesos empresariales bajo RUP y UML, el Diagrama de Clases del Negocio (o Modelo de Objetos del Negocio) representa las entidades, documentos y conceptos abstractos de información que los trabajadores del negocio manipulan diariamente para ejecutar sus labores. A diferencia de un diagrama de diseño de software tecnológico, estas clases no modelan tablas de base de datos ni implementaciones de código, sino abstracciones estructuradas del mundo real (como inventarios, ventas en mostrador, órdenes de abastecimiento, reclamos y comprobantes) con sus atributos esenciales y relaciones de asociación funcional (Pressman y Maxim, 2021).

\section{CAP\'ITULO 4: CONCLUSIONES}

De conformidad con los objetivos específicos planteados para el desarrollo del Sistema de Gestión de Inventario para la juguetería minorista ``Mundo del Juguete'', se formulan las siguientes conclusiones técnicas y académicas:

\begin{enumerate}
    \item \textbf{Automatización eficaz del inventario y compras (en respuesta al OE1):} Se logró sistematizar de manera integral el control de existencias físicas mediante el cálculo dinámico de umbrales de stock mínimo y la generación asistida de órdenes de abastecimiento. La inclusión de alertas automáticas elimina el riesgo de quiebres imprevistos de stock en épocas de alta demanda (como campañas navideñas o feriados), permitiendo que el encargado de almacén y el administrador sincronicen recepciones de mercancía con el kardex de forma inmediata y verificable.
    \item \textbf{Optimización del punto de venta y emisión legal de comprobantes (en respuesta al OE2):} La implementación del módulo de punto de venta (POS) garantiza la validación de disponibilidad de juguetes en tiempo real antes de confirmar cualquier transacción comercial, impidiendo la sobreventa o reservas inconsistentes. Asimismo, la integración del cálculo automatizado de subtotales, IGV y vueltos junto con la emisión de comprobantes autorizados (boletas y facturas) agilizó el tiempo de atención en caja a menos de 45 segundos por cliente.
    \item \textbf{Trazabilidad total entre requerimientos, dominio y código (en respuesta al OE3):} La construcción de matrices de trazabilidad biunívocas (RF/RNF frente a CUS, clases de dominio e interfaces de usuario) certificó que el 100\% de las necesidades identificadas en el negocio de la juguetería cuentan con un respaldo directo en el modelo de software. Esta trazabilidad reduce la incertidumbre en los mantenimientos evolutivos y asegura una auditoría interna rigurosa ante cualquier discrepancia física de mercancía.
    \item \textbf{Solidez y escalabilidad de la arquitectura en tres capas bajo MVC y Laravel (en respuesta al OE4):} El diseño arquitectural desacoplado en tres capas (Presentación en Blade, Lógica de Negocio en controladores transaccionales y Dominio persistente en Eloquent ORM sobre MySQL) demostró ser altamente eficiente. Las dependencias unidireccionales (\guillemotleft use\guillemotright, \guillemotleft access\guillemotright, \guillemotleft import\guillemotright) garantizan que cambios cosméticos en la interfaz de usuario no degraden las reglas transaccionales ni comprometan la integridad referencial de los datos.
    \item \textbf{Aseguramiento de la calidad mediante el enfoque metodológico Cascada y pruebas formales:} La adopción del modelo secuencial Waterfall permitió cerrar y validar cada fase de la ingeniería de software con rigor matemático y conceptual. La ejecución de la batería de casos de prueba (CP-01 a CP-06) constató una tasa de éxito del 100\% en las operaciones críticas de autenticación, control de stock, cobro transaccional y reabastecimiento, entregando una solución robusta y lista para su implantación en producción.
\end{enumerate}

\section{CAP\'ITULO 5: RECOMENDACIONES}

En correspondencia directa y biunívoca con cada una de las conclusiones formuladas, se proponen las siguientes recomendaciones técnicas y de gestión para la evolución operativa del sistema:

\begin{enumerate}
    \item \textbf{Calibración estacional de umbrales y acuerdos SLA de abastecimiento (correlacionada con la Conclusión 1):} Se recomienda a la gerencia de la juguetería recalibrar los parámetros de stock mínimo de forma bimensual mediante análisis predictivo de rotación (clasificación ABC), diferenciando productos de temporada de aquellos de venta continua. Asimismo, se aconseja formalizar acuerdos de nivel de servicio (SLA) con los proveedores para garantizar entregas en menos de 48 horas tras la emisión de órdenes de compra.
    \item \textbf{Integración de hardware POS avanzado y pasarelas de pago digitales (correlacionada con la Conclusión 2):} Para potenciar la velocidad de atención en mostrador, se sugiere integrar lectores ópticos de código de barras bidimensionales (código QR / DataMatrix), impresoras térmicas de tickets bajo protocolo ESC/POS y pasarelas de pago electrónico nativas (como Yape, Plin o POS Niubiz) comunicadas por API REST directamente con el controlador de cobros de Laravel.
    \item \textbf{Auditorías físicas rotativas asistidas por terminales móviles (correlacionada con la Conclusión 3):} Se recomienda planificar conteos físicos cíclicos semanales para subconjuntos específicos de categorías de juguetes de alto valor, utilizando dispositivos móviles o tabletas que consulten el kardex del sistema en tiempo real. Esto permitirá detectar inmediatamente mermas o productos dañados sin requerir el cierre total del establecimiento.
    \item \textbf{Optimización de índices y particionamiento en base de datos MySQL (correlacionada con la Conclusión 4):} A medida que el volumen histórico de ventas y detalles crezca en el transcurso de los ejercicios fiscales, se recomienda crear índices compuestos en las tablas transaccionales (\texttt{ventas}, \texttt{detalle\_ventas}, \texttt{movimientos\_kardex}) y configurar tareas programadas de mantenimiento en Laravel (\emph{Artisan commands}) para optimizar el almacenamiento y la velocidad de consultas analíticas.
    \item \textbf{Automatización de pipelines de Integración Continua (CI/CD) (correlacionada con la Conclusión 5):} Se aconseja incorporar un flujo de trabajo automatizado con GitHub Actions en el repositorio del proyecto, ejecutando los casos de prueba de PHPUnit y análisis estático con PHPStan antes de permitir fusiones (\emph{merge}) hacia la rama principal (\texttt{main}), asegurando que ningún cambio futuro degrade las funcionalidades validadas en este informe.
\end{enumerate}
