\section*{Resumen}
\addcontentsline{toc}{section}{Resumen}

El presente proyecto de investigación expone el desarrollo de un Sistema de
Gestión de Inventario para una juguetería minorista, diseñado bajo el
paradigma de la Programación Orientada a Objetos (POO) empleando el lenguaje
PHP a través del framework \emph{Laravel}. La propuesta surge ante las
deficiencias identificadas en el control manual de existencias y la falta de
sincronización en tiempo real, lo cual impacta negativamente la rentabilidad
empresarial. A través de una arquitectura \emph{Modelo-Vista-Controlador}
(MVC) que implementa el mapeo objeto-relacional \emph{Eloquent ORM} y las
plantillas de vista \emph{Blade}, se ofrece una aplicación web modular,
escalable y altamente portable. La persistencia estructurada y el control
jerárquico por categorías y marcas aseguran la integridad de los datos,
optimizando las auditorías y permitiendo una toma de decisiones informada
basada en reportes automatizados.

\emph{Palabras clave:} inventario, Programación Orientada a Objetos, PHP,
Laravel, Eloquent, juguetería.

\section{Problemática}

La gestión de inventarios en una juguetería minorista enfrenta desafíos
críticos debido a la alta rotación de productos y la diversidad de categorías
que deben administrarse. Actualmente, el uso de métodos manuales o registros en
hojas de cálculo aisladas ha evidenciado limitaciones estructurales en el
modelo operativo (Welling y Thompson, 2017). Esta práctica convencional genera
tres problemas operativos fundamentales que afectan la rentabilidad y la
eficiencia del negocio:

\begin{itemize}
  \item \textbf{Deficiencia en el control de stock por categorías y marcas:}
        la ausencia de una clasificación sistematizada impide una organización
        jerárquica eficiente, dificultando la localización y el seguimiento de
        juguetes según su fabricante o grupo de edad.
  \item \textbf{Invisibilidad de existencias en tiempo real:} la falta de
        sincronización entre las ventas realizadas y el registro de almacén
        imposibilita conocer la disponibilidad inmediata de los productos.
  \item \textbf{Ineficiencia en procesos manuales e inventarios físicos:}
        el procesamiento manual de ventas y la ejecución de auditorías físicas
        periódicas consumen recursos humanos de forma excesiva.
\end{itemize}

% ============================================================
\section{Importancia de la Solución}

El Sistema de Gestión de Inventario para juguetería resolverá la fragmentación
de datos mediante la centralización de operaciones en una aplicación web
nativa e independiente basada en el paradigma de la Programación Orientada a
Objetos (POO) mediante el framework Laravel (Stauffer, 2019). Al prescindir de
dependencias de escritorio pesadas, la solución garantiza agilidad, control
preciso de existencias y portabilidad, requiriendo únicamente un servidor web
con PHP y un gestor de base de datos MySQL.

% ============================================================
\section{Delimitación de Objetivos}

\subsection{Objetivo General}

Desarrollar una aplicación web utilizando PHP y Laravel que automatice la
gestión de inventario de una juguetería, optimizando el control de productos,
stock y categorías mediante una arquitectura modular orientada a objetos que
garantice la integridad y persistencia de la información.

\subsection{Objetivos Específicos}

\begin{itemize}
  \item Modelar el dominio del negocio de la juguetería mediante los pilares
        de la POO (Abstracción, Encapsulamiento, Herencia y Polimorfismo).
  \item Diseñar e implementar una capa de persistencia relacional robusta
        mediante \emph{Eloquent ORM} sobre un motor de base de datos MySQL.
  \item Construir una interfaz web moderna y modular con las plantillas
        \emph{Blade}, HTML5, CSS y JavaScript.
\end{itemize}

% ============================================================
\section{Marco Teórico}

Para fundamentar la construcción del software bajo estándares técnicos de la
industria, se describen las tecnologías y conceptos asociados a PHP y Laravel
que constituirán la estructura del sistema (PHP Documentation Group, 2024):

\begin{description}
  \item[PHP:] lenguaje de scripting del lado del servidor que provee un motor
        de ejecución síncrono, la gestión de memoria y las APIs estándares
        de control de datos sin requerir servidores externos.
  \item[Laravel:] framework MVC para PHP que facilita el desarrollo de
        aplicaciones web mediante \emph{rutas}, \emph{controladores} y
        \emph{migraciones} de base de datos (Stauffer, 2019).
  \item[Herencia y Polimorfismo:] mecanismos de POO que se emplearán para
        definir una clase base denominada ``Producto'' y especializar
        comportamientos mediante subclases (Welling y Thompson, 2017).
  \item[Eloquent ORM:] mapeo objeto-relacional de Laravel que actúa como
        puente de comunicación directo con el motor de base de datos
        relacional MySQL.
  \item[Blade \& Bootstrap:] motor de plantillas de Laravel combinado con el
        framework CSS Bootstrap para la maquetación de la interfaz web.
\end{description}

\subsection{Reglas de Negocio}

De acuerdo con la normativa operativa del sistema de gestión para la juguetería, se han identificado y descrito las siguientes reglas de negocio fundamentales:

\subsubsection{Regla de estímulo y respuesta (RN-01)}
Si el proveedor no confirma la solicitud de abastecimiento en un plazo máximo de 72 horas, el sistema genera automáticamente una alerta de retraso de pedido y la notifica al panel del Administrador para que tome acciones preventivas.

\subsubsection{Regla de operación (RN-02)}
Para concretar y registrar una venta en el sistema, el Vendedor o Cajero debe haber iniciado sesión de manera autenticada, y el producto seleccionado debe contar con un nivel de stock disponible mayor a cero en el registro físico del almacén.

\subsubsection{Regla de estructura (RN-03)}
Por cada transacción de venta completada, el sistema genera de forma obligatoria un comprobante electrónico con un número de serie correlativo único. Un mismo comprobante puede contener múltiples productos diferentes sin límite de líneas, siempre y cuando la cantidad de cada uno no exceda las existencias en inventario.

\subsubsection{Regla de inferencia (RN-04)}
Un juguete o producto cuyo inventario físico no presente ningún movimiento de salida (cero ventas) durante un periodo continuo de 6 meses, es catalogado y etiquetado lógicamente por el sistema como «Producto de baja rotación» para posteriores auditorías.

\subsubsection{Regla de cálculo (RN-05)}
El cálculo del monto total de una venta se obtiene sumando los subtotales de cada ítem en el detalle de la venta. El subtotal de cada ítem se define mediante la fórmula matemática: \\
\textbf{Subtotal = Precio Unitario $\times$ Cantidad}\\
\textit{Nota: El Impuesto General a las Ventas (IGV del 18\%) ya se encuentra gravado e incluido en el Precio Unitario final del catálogo.}

\subsection{Requerimientos Funcionales}

Los requerimientos funcionales (RF) describen las funciones que el sistema
debe proporcionar para apoyar los seis casos de uso. Se identifican con el
prefijo RF, seguido de un número de dos dígitos y una descripción del
comportamiento esperado. Los códigos CUN-01 a CUN-06 se mantienen para
relacionar cada grupo con su caso de uso.

\subsubsection{CUN-01: Gestionar Ventas}

\begin{itemize}
  \item \textbf{RF-01: Inicio de Sesión del Personal:} El sistema debe permitir el acceso exclusivo a los usuarios autorizados (vendedor o cajero) mediante credenciales válidas antes de permitir operaciones de venta.
  \item \textbf{RF-02: Selección de Productos:} El sistema debe permitir al vendedor buscar, seleccionar o ingresar manualmente los juguetes que el cliente desea adquirir.
  \item \textbf{RF-03: Validación de Stock en Tiempo Real:} El sistema debe comprobar de manera automática si existe la cantidad suficiente de stock disponible para cada juguete solicitado antes de concretar la transacción.
  \item \textbf{RF-04: Procesamiento de Venta y Comprobante:} El sistema debe registrar formalmente la transacción de venta vinculando al cliente, los productos, el total a pagar y emitir el mensaje de confirmación de venta exitosa.
  \item \textbf{RF-05: Actualización Automática del Inventario por Venta:} El sistema debe descontar de manera automática las unidades vendidas del inventario general de productos una vez que la venta ha sido procesada con éxito.
  \item \textbf{RF-06: Manejo de Excepciones por Stock Insuficiente:} El sistema debe mostrar un mensaje de error o alerta cuando la cantidad solicitada supere el stock disponible o si ocurre un fallo de conexión al procesar el registro.
\end{itemize}

\subsubsection{CUN-02: Gestionar abastecimiento}

\begin{itemize}
  \item \textbf{RF-07: Detección de Baja Disponibilidad de Stock:} El sistema o el administrador deben permitir revisar el catálogo de productos para detectar niveles bajos de existencia o la necesidad de nuevos artículos, previniendo quiebres de inventario.
  \item \textbf{RF-08: Cotización con Proveedores:} El sistema debe permitir registrar y gestionar el proceso de cotización de los productos seleccionados con los proveedores externos.
  \item \textbf{RF-09: Emisión de Pedidos Formales de Compra:} El sistema debe permitir al administrador registrar y emitir las órdenes de compra o pedidos formales dirigidos a los proveedores.
  \item \textbf{RF-10: Recepción de Nueva Mercancía:} El sistema debe permitir al administrador o al encargado de almacén registrar la llegada y recepción física de la mercancía despachada por el proveedor en el establecimiento.
  \item \textbf{RF-11: Actualización de Niveles de Stock por Abastecimiento:} El sistema debe registrar de forma automática la entrada de la nueva mercancía para incrementar y actualizar en tiempo real los niveles de inventario de los juguetes.
\end{itemize}

\subsubsection{CUN-03: Controlar inventario}

\begin{itemize}
  \item \textbf{RF-12: Acceso al Módulo de Inventario:} El sistema debe permitir el acceso del administrador o vendedor al módulo especializado de control de inventario.
  \item \textbf{RF-13: Registro de Auditorías Físicas:} El sistema debe permitir registrar los resultados de las auditorías físicas realizadas a los juguetes almacenados en la tienda.
  \item \textbf{RF-14: Registro de Mermas y Juguetes Rotos:} El sistema debe permitir identificar y registrar formalmente las pérdidas, mermas o artículos dañados encontrados durante las revisiones.
  \item \textbf{RF-15: Actualización de Niveles Mínimos de Stock y Existencias:} El sistema debe permitir actualizar de manera precisa los niveles mínimos de stock y los registros de existencias con base en los datos de la auditoría.
  \item \textbf{RF-16: Emisión de Informes de Inventario Disponible:} El sistema debe guardar los cambios realizados y emitir un informe actualizado del inventario disponible tras concluir el control.
\end{itemize}

\subsubsection{CUN-04: Gestionar devoluciones y cambios}

\begin{itemize}
  \item \textbf{RF-17: Recepción de Solicitudes de Devolución:} El sistema debe permitir registrar las solicitudes presentadas por los clientes cuando reportan un juguete defectuoso o desean realizar un cambio o reembolso.
  \item \textbf{RF-18: Verificación de Comprobante y Estado del Producto:} El sistema debe permitir verificar la validez del comprobante de venta original y registrar el estado físico del juguete para evaluar si cumple con las condiciones de devolución.
  \item \textbf{RF-19: Validación de Políticas y Plazos:} El sistema debe validar que el producto se encuentre dentro del plazo permitido para devoluciones y descartar daños ocasionados por mal uso del cliente.
  \item \textbf{RF-20: Procesamiento de Solución (Cambio o Reembolso):} El sistema debe permitir al vendedor procesar la opción seleccionada, ya sea generando un cambio de producto o aplicando un reembolso al cliente.
  \item \textbf{RF-21: Generación de Notas y Actualización de Inventario por Devolución:} El sistema debe actualizar de forma automática el inventario o generar la nota de crédito/débito correspondiente según la solución aplicada a la devolución.
\end{itemize}

\subsubsection{CUN-05: Flujo de Venta y Reposición}

\begin{itemize}
  \item \textbf{RF-22: Registro de Venta y Descuento Automático:} El sistema debe permitir al vendedor registrar la venta de los juguetes y descontar de forma automática las existencias del stock.
  \item \textbf{RF-23: Cobro y Emisión de Comprobante:} El sistema debe permitir al cajero procesar el cobro de la transacción y generar el comprobante de pago para el cliente.
  \item \textbf{RF-24: Solicitud y Registro de Pedidos de Stock:} El sistema debe permitir al administrador ingresar y registrar las solicitudes de abastecimiento o pedidos de nuevos productos.
  \item \textbf{RF-25: Recepción y Actualización Final de Inventario:} El sistema debe permitir al encargado de almacén registrar la recepción de la mercancía para guardar y actualizar definitivamente el inventario disponible.
\end{itemize}

\subsubsection{CUN-06: Actores externos de negocio}

\begin{itemize}
  \item \textbf{RF-26: Registro de Solicitud de Compra del Cliente:} El sistema debe permitir registrar las solicitudes o peticiones de compra iniciales realizadas por los clientes en el establecimiento.
  \item \textbf{RF-27: Gestión de Atención de Ventas:} El sistema debe permitir al vendedor procesar y registrar la atención brindada al cliente durante el proceso comercial.
  \item \textbf{RF-28: Constancia de Entrega al Cliente:} El sistema debe registrar la confirmación de que el cliente ha recibido satisfactoriamente su compra.
  \item \textbf{RF-29: Emisión de Pedidos de Stock a Proveedores:} El sistema debe permitir al administrador generar y enviar solicitudes de reabastecimiento hacia los proveedores.
  \item \textbf{RF-30: Registro de Envío y Recepción de Proveedores:} El sistema debe permitir registrar el despacho y envío de mercancía realizado por el proveedor.
  \item \textbf{RF-31: Registro de Ingreso de Mercancía en el Sistema:} El sistema debe registrar formalmente el ingreso de la nueva mercancía proveniente de la cadena de suministro para actualizar las existencias.
\end{itemize}

\subsection{Requerimientos No Funcionales}

Los requerimientos no funcionales (RNF) establecen las condiciones de calidad
que debe cumplir la plataforma. Se identifican con el prefijo RNF, seguido de
un número de dos dígitos.

\begin{itemize}
  \item \textbf{RNF-01: Rendimiento y Tiempos de Ejecución:} La plataforma debe ser capaz de procesar las consultas de stock, las transacciones de venta y las actualizaciones de inventario en un lapso máximo de 2 segundos bajo condiciones habituales de trabajo.
  \item \textbf{RNF-02: Disponibilidad Operativa:} El sistema tiene que asegurar un funcionamiento continuo durante las horas de atención al público, evitando interrupciones que perjudiquen las operaciones en caja o almacén.
  \item \textbf{RNF-03: Seguridad y Autenticación:} Las secciones sensibles de la aplicación (tales como la auditoría de inventario, el abastecimiento y los permisos especiales) deben protegerse mediante perfiles de usuario y claves cifradas asignadas a cada rol (Administrador, Vendedor, Cajero y Encargado de Almacén).
  \item \textbf{RNF-04: Soporte Concurrente:} La infraestructura del sistema debe permitir que varios colaboradores trabajen al mismo tiempo (por ejemplo, operarios registrando ventas de forma paralela mientras se actualiza el almacén) sin provocar bloqueos ni alterar la integridad de los datos.
  \item \textbf{RNF-05: Experiencia de Usuario y Usabilidad:} El diseño visual de la interfaz debe ser sencillo y amigable, permitiendo que el personal se adapte rápidamente al software sin requerir entrenamientos prolongados y agilizando la ejecución de tareas frecuentes.
  \item \textbf{RNF-06: Resguardo y Respaldo de la Información:} El sistema debe programar copias de seguridad automáticas todos los días (abarcando catálogos, registros de ventas y auditorías) para prevenir pérdidas de datos ante imprevistos técnicos o cortes imprevistos de energía.
\end{itemize}

\section{Diseño de la Solución}

\subsection{Diagrama de Clases UML (Estructura de Paquetes)}

Para asegurar la escalabilidad del sistema y cumplir con el Principio de
Responsabilidad Única (SRP), el código fuente se ha organizado estrictamente
separando las entidades de dominio frente a los componentes de infraestructura
técnica y la interfaz web (Larman, 2004). Como se observa en el diagrama de
clases, la arquitectura se divide en los siguientes paquetes principales:

\begin{itemize}
  \item \textbf{Models / Entidades:} representan las entidades del negocio
        (\emph{Cliente, Producto, Usuario, Venta} y \emph{DetalleVenta}),
        encapsulando sus atributos mediante los modelos de \emph{Eloquent}.
  \item \textbf{Controllers (MVC):} centralizan la lógica de negocio y las
        operaciones transaccionales hacia la base de datos (ej.
        \emph{ClienteController, ProductoController}), aislando las sentencias
        SQL del resto del sistema.
  \item \textbf{Views (Blade):} agrupan las plantillas web, donde la vista
        principal actúa como contenedor para enrutar hacia paneles como
        \emph{Ventas} o \emph{Productos}.
  \item \textbf{Database y Services:} proveen servicios transversales, como la
        conexión mediante \emph{Eloquent ORM}, el manejo de la sesión de
        usuario activo y herramientas como generación de tickets y utilidades
        de seguridad.
\end{itemize}

\subsection{Diagrama de Base de Datos (ERD Conceptual)}

El modelo entidad-relación (ERD) ha sido diseñado garantizando la integridad
referencial y la normalización de los datos. La arquitectura de la base de
datos se estructura en torno a las siguientes entidades clave y sus respectivos
tipos de datos:

\begin{itemize}
  \item \textbf{Tablas maestras:} entidades como \emph{usuarios},
        \emph{clientes} y \emph{categorias} que almacenan la información
        descriptiva y de acceso al sistema, utilizando llaves primarias
        auto-incrementables.
  \item \textbf{Gestión de inventario:} la tabla \emph{productos} centraliza el
        catálogo, stock (\emph{INT}) y precios (\emph{DECIMAL}), vinculándose
        directamente con su respectiva categoría mediante la llave foránea
        \emph{idCategoria}.
  \item \textbf{Núcleo transaccional:} compuesto por las tablas \emph{ventas}
        (cabecera) y \emph{detalle ventas} (cuerpo). La cabecera registra al
        responsable y al comprador mediante sus llaves foráneas, capturando la
        hora exacta (\emph{TIMESTAMP}). El detalle desglosa cada ítem vendido
        permitiendo calcular los subtotales con precisión monetaria
        (\emph{DECIMAL}) y mantener un historial de ventas exacto.
\end{itemize}

\section{Conclusiones}

En conclusión, la construcción del diagrama de clases para cada entidad principal
(inventario de productos, ventas y detalle de ventas, compras y detalle de
compras, devoluciones, usuarios y clientes) permitió visualizar claramente las
acciones operativas, mostrando la intervención precisa de cada actor dentro del
negocio.

Asimismo, los diagramas de actividades elaborados para los seis casos de uso
(CUN-01 a CUN-06) facilitaron la comprensión del desarrollo secuencial de los procesos de
ventas, abastecimiento y control de inventario, así como la gestión de devoluciones y cambios.
Esto evidenció de forma gráfica la interacción fluida entre los trabajadores internos
y los actores externos, identificando decisiones, acciones y puntos de control clave en
cada proceso.

Por otra parte, el análisis integrado de los diagramas de clases y de actividades
demostró que un mismo proceso de negocio frecuentemente involucra a múltiples entidades
relacionadas, como ocurre en la sinergia entre ventas y su respectivo detalle, o en
el módulo de compras. Esto ratifica la necesidad metodológica de mantener una estricta
coherencia entre ambos diagramas para reflejar fielmente la lógica operativa del
establecimiento.

De igual manera, esta etapa de modelado permitió constatar que la abstracción del
negocio no solo sirve para documentar los procedimientos actuales de la tienda
Mundo del Juguete, sino que también estructura las bases para identificar y
organizar los requerimientos del futuro producto de software. En consecuencia, se
determinan de manera óptima qué procesos operativos se benefician al ser
automatizados para mejorar su rendimiento.

Adicionalmente, el trazo de los diagramas de actividades facilitó la identificación
anticipada de escenarios de excepción o flujos alternativos, tales como la carencia de
stock suficiente, la presentación de comprobantes inválidos o discrepancias en la
recepción de mercancía. Esto proveyó directrices claras sobre las validaciones y el
manejo de errores que el futuro sistema deberá implementar.

Finalmente, la identificación exhaustiva de 31 requerimientos funcionales y 6
requerimientos no funcionales, en conjunto con su matriz de trazabilidad vinculada a
actores, casos de uso y reglas de negocio, consolida una base documental sólida y
verificable. Esta estructura garantiza un alineamiento total entre las necesidades del
negocio y el posterior diseño e implementación de la solución de software.

\section{Recomendaciones}

\begin{itemize}
  \item Implementar en el sistema validaciones automáticas de stock disponible
        antes de confirmar cualquier venta, mostrando mensajes de error claros
        cuando la cantidad solicitada supere las existencias.
  \item Diseñar un módulo de devoluciones que valide la autenticidad del
        comprobante de pago y verifique el plazo permitido y el estado del
        juguete antes de aprobar un cambio o reembolso.
  \item Establecer un control de calidad en la recepción de mercancía que
        permita registrar las diferencias entre lo pedido y lo recibido,
        actualizando automáticamente el inventario.
  \item Garantizar la coherencia entre los diagramas de clases y de actividades
        y su implementación en el sistema, de modo que las entidades y los
        procesos modelados se correspondan con el software final.
  \item Desarrollar reportes automatizados de ventas, compras y stock que
        faciliten la toma de decisiones informadas y las auditorías periódicas.
  \item Capacitar al personal (vendedor, cajero, administrador y encargado de
        almacén) en el uso del sistema para asegurar un registro consistente de
        la información.
\end{itemize}
