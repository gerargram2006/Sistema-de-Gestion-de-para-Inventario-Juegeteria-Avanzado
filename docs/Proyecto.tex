\section{Resumen}

\begin{abstract}
  \noindent El presente proyecto de investigación expone el desarrollo de un
  Sistema de Gestión de Inventario para una juguetería minorista, diseñado bajo
  el paradigma de la Programación Orientada a Objetos (POO) empleando la
  plataforma Java SE. La propuesta surge ante las deficiencias identificadas en
  el control manual de existencias y la falta de sincronización en tiempo real,
  lo cual impacta negativamente la rentabilidad empresarial. A través de una
  arquitectura limpia y modular que implementa la API nativa JDBC y la librería
  gráfica Java Swing, se ofrece una aplicación de escritorio independiente,
  ágil y altamente portable. La persistencia estructurada y el control
  jerárquico por categorías y marcas aseguran la integridad de los datos,
  optimizando las auditorías y permitiendo una toma de decisiones informada
  basada en reportes automatizados.

  \medskip
  \noindent\textbf{Palabras clave:} inventario, Programación Orientada a
  Objetos, Java SE, JDBC, Java Swing, juguetería.
\end{abstract}

\section{Problemática}

La gestión de inventarios en una juguetería minorista enfrenta desafíos
críticos debido a la alta rotación de productos y la diversidad de categorías
que deben administrarse. Actualmente, el uso de métodos manuales o registros en
hojas de cálculo aisladas ha evidenciado limitaciones estructurales en el
modelo operativo (Schildt, 2018). Esta práctica convencional genera tres
problemas operativos fundamentales que afectan la rentabilidad y la eficiencia
del negocio:

\begin{itemize}
  \item \textbf{Deficiencia en el control de stock por categorías y marcas:}
        la ausencia de una clasificación sistematizada impide una organización
        jerárquica eficiente, dificultando la localización y el seguimiento de
        juguetes según su fabricante o grupo de edad.
  \item \textbf{Invisibilidad de existencias en tiempo real:} la falta de
        sincronización entre las ventas realizadas y el registro de almacén
        imposibilita conocer la disponibilidad inmediata de los productos.
  \item \textbf{Ineficiencia en procesos manuales e inventarios físicos:}
        el procesamiento manual de ventas y la ejecución de auditorías físicas
        periódicas consumen recursos humanos de forma excesiva.
\end{itemize}

\section{Importancia de la Solución}

El Sistema de Gestión de Inventario para juguetería resolverá la fragmentación
de datos mediante la centralización de operaciones en una aplicación de
escritorio nativa e independiente basada en el paradigma de la Programación
Orientada a Objetos (POO) (Deitel \& Deitel, 2017). Al prescindir de
dependencias externas pesadas, la solución garantiza agilidad, control preciso
de existencias y portabilidad, requiriendo únicamente el entorno de ejecución
de Java (JRE).

\section{Delimitación de Objetivos}

\subsection{Objetivo General}

Desarrollar una aplicación de escritorio nativa utilizando Java SE que
automatice la gestión de inventario de una juguetería, optimizando el control
de productos, stock y categorías mediante una arquitectura modular orientada a
objetos que garantice la integridad y persistencia de la información.

\subsection{Objetivos Específicos}

\begin{itemize}
  \item Modelar el dominio del negocio de la juguetería mediante los pilares
        de la POO (Abstracción, Encapsulamiento, Herencia y Polimorfismo).
  \item Diseñar e implementar una capa de persistencia relacional robusta
        utilizando exclusivamente la API nativa JDBC.
  \item Construir una interfaz gráfica de usuario (GUI) modular con la
        librería Java Swing.
\end{itemize}

\section{Marco Teórico}

Para fundamentar la construcción del software bajo estándares técnicos de la
industria, se describen las tecnologías y conceptos nativos de Java SE que
constituirán la estructura del sistema (Oracle, 2021):

\begin{description}
  \item[Java SE (Standard Edition):] plataforma base de desarrollo que provee
        el motor de ejecución síncrono, la gestión de memoria y las APIs
        estándares de control de datos sin requerir servidores externos.
  \item[Herencia y Polimorfismo:] mecanismos de POO que se emplearán para
        definir una clase abstracta base denominada ``Producto'' y
        especializar comportamientos mediante subclases (Deitel \& Deitel,
        2017).
  \item[Java Swing \& AWT:] librerías nativas empleadas para la maquetación de
        la interfaz gráfica.
  \item[JDBC API:] API estándar de Java que actúa como puente de comunicación
        directo con el motor de base de datos relacional (Baeldung, 2023).
  \item[Java Collections Framework:] estructuras de datos dinámicas
        (ArrayList, Map) utilizadas para almacenar y manipular eficientemente
        en memoria las colecciones de productos y el inventario general.
\end{description}

\subsection{Diagrama de Clases UML (Estructura de Paquetes)}

Para asegurar la escalabilidad del sistema y cumplir con el Principio de
Responsabilidad Única (SRP), el código fuente se ha organizado estrictamente
separando las entidades de dominio frente a los componentes de infraestructura
técnica y la interfaz gráfica (Larman, 2004). Como se observa en el diagrama de
clases, la arquitectura se divide en los siguientes paquetes principales:

\begin{itemize}
  \item \textbf{Models:} contiene las clases que representan las entidades del
        negocio (\emph{Cliente, Producto, Usuario, Venta} y
        \emph{DetalleVenta}), encapsulando sus atributos.
  \item \textbf{DAO (Data Access Object):} centraliza todas las operaciones
        transaccionales hacia la base de datos (ej. \emph{ClienteDAO,
        ProductoDAO}), aislando las sentencias SQL del resto del sistema
        (Baeldung, 2023).
  \item \textbf{Views:} agrupa las interfaces gráficas construidas con Java
        Swing, donde \emph{MainView} actúa como contenedor principal para
        enrutar hacia paneles como \emph{VentasView} o \emph{ProductosView}.
  \item \textbf{Database y Util:} proveen servicios transversales, como la
        clase \emph{ConexionDB} para establecer el enlace relacional, el manejo
        de \emph{Session} para el usuario activo y herramientas como
        \emph{TicketGenerator} y \emph{SecurityUtils}.
\end{itemize}

\subsection{Diagrama de Base de Datos (ERD Conceptual)}

El modelo entidad-relación (ERD) ha sido diseñado garantizando la integridad
referencial y la normalización de los datos. La arquitectura de la base de
datos se estructura en torno a las siguientes entidades clave y sus respectivos
tipos de datos:

\begin{itemize}
  \item \textbf{Tablas maestras:} entidades como \emph{usuarios}, \emph{clientes}
        y \emph{categorias} que almacenan la información descriptiva y de
        acceso al sistema, utilizando llaves primarias auto-incrementables.
  \item \textbf{Gestión de inventario:} la tabla \emph{productos} centraliza el
        catálogo, stock (\emph{INT}) y precios (\emph{DECIMAL}), vinculándose
        directamente con su respectiva categoría mediante la llave foránea
        \emph{idCategoria}.
  \item \textbf{Núcleo transaccional:} compuesto por las tablas \emph{ventas}
        (cabecera) y \emph{detalle ventas} (cuerpo). La cabecera registra al
        responsable y al comprador mediante sus llaves foráneas, capturando la
        hora exacta (\emph{TIMESTAMP}). El detalle desglosa cada ítem vendido
        permitiendo calcular los subtotales con precisión monetaria
        (\emph{DECIMAL}) y mantener un historial de ventas exacto.
\end{itemize}
